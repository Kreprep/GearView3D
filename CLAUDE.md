# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Scope

GearView3D is a thesis prototype for browser-based forklift familiarization training. It supports learner modules, guided checklists, parts identification, progress tracking, quizzes, final assessment review, and local admin content management. It is a preparatory learning tool, not a certification simulator (no TESDA certification implied).

**Forklift only.** After the final thesis defense (2026-09) the panel narrowed the app to the forklift. Everything built to make it reusable for other equipment was removed: the equipment catalog, the admin equipment picker, every `equipmentId` column, query parameter, prop and URL segment, and the code that fitted non-forklift 3D models. `Equipment` is now **one row of configuration**, not a dimension content is scoped by. Do not reintroduce equipment scoping, and do not replace it with `'forklift'` literals in the logic: that string belongs only in seed data (`data/equipment.js` and the stock content files), migration SQL, and the legacy shims (`legacyRedirect()` in `lib/router.js`, `migrateParts()`).

**Post-defense revisions** (panel of 2026-09-24) are designed in `docs/revisions/post-defense-plan.md`, and every change made for them is recorded in `docs/revisions/revision-log.md`, which the thesis's list of revisions is compiled from. Both files are permanent. Any commit that works on a panel item adds a row to that item's table in the log (date, what changed in plain language, where in the app, commit hash) and updates the summary status. If the implementation departs from the plan, update the plan too. The plan has no dates on purpose: the team sets the pace, since revisions need the professors' sign-off.

**Full-stack:** `frontend/` (React + Vite) plus `backend/` (Express 5 + Prisma 6 + PostgreSQL, plain ESM Node, no TypeScript). Both must run for the app to work; the Vite dev server proxies `/api` to the backend (port 4000, see `vite.config.js`).

**Deployment** is `docker-compose.yml` at the repo root — postgres + backend + an nginx container serving the built frontend. Both images build from the **repo root**, not their own folder, because `prisma/seed.js` imports `frontend/src/data/*.js` directly. In production nginx does what the Vite proxy does in development (`frontend/nginx.conf`: `/api` to the backend, everything else falling back to `index.html` for the pushState router), so a reverse proxy in front only needs one upstream. `backend/docker-entrypoint.sh` runs `prisma migrate deploy` (never `migrate dev`) then the seed on every boot.

A live instance of this stack runs on a homelab LXC container (`gearview3d.lindenwood53.vip`, behind a Caddy reverse proxy), redeployed via `git pull && docker compose up -d --build` using a read-only GitHub deploy key on the box — see README's **Live instance** section for the non-secret summary. Full LXC specs and credentials live in the private homelab doc (private documentation), never in this repo.

## Commands

Frontend (from `frontend/`):

```bash
npm install
npm run dev       # Vite dev server (usually http://localhost:5173), proxies /api -> :4000
npm run build     # production build
npm run lint      # ESLint (flat config, eslint.config.js)
```

Backend (from `backend/`; needs `backend/.env` — copy `.env.example`, set the PostgreSQL password in `DATABASE_URL` percent-encoded):

```bash
npm install
npx prisma migrate dev   # create/update the gearview3d database schema
npm run seed             # idempotent: create-if-missing only, never overwrites admin edits
npm run dev              # API on http://localhost:4000 (node --watch)
npm run studio           # Prisma Studio DB browser
```

`npm test` runs each package's tests (`node --test`): `frontend/src/**/*.test.js` and `backend/test/*.test.js`.

**Content export/import** (`backend/scripts/`, `npm run content:export` / `content:import`) moves admin-edited rows between databases as `backend/prisma/content-export.json` — the only way admin edits reach another machine, since they live in the DB and not in the repo. `contentTables.js` lists the tables and the order they import in (FK-safe); `User` and `ProgressSnapshot` are deliberately excluded, as is `Course.draft`. The import **overwrites**, which is the one place that differs from the create-if-missing seed. Adding a content table means adding it to `contentTables.js`, in dependency order.

## Architecture

### `lib/api.js` is the seam; the backend owns the data
`frontend/src/lib/api.js` is a thin fetch client — the only file that talks HTTP. Page components call its named functions (`loginUser`, `getTrainingModules`, `adminSaveHotspotDraft`, ...) and must not fetch directly. Auth is a JWT stored in `localStorage` (`gearview_token`), sent as a Bearer header via the module-level `setAuthToken()`. Tokens last `TOKEN_LIFETIME` (7 days, `backend/src/lib/auth.js`). **A 401 ends the session:** when a request carrying the current token gets one, `request()` fires `gearview-session-expired` and `App.jsx` signs out and shows the sign-in page with an expiry notice. Before that, a cached `gearview_user` skipped the session check on load, so an expired token stranded the learner on signed-in pages with every fetch failing. It follows that the backend must answer 401 **only** for a dead session (missing, expired or invalid token, deleted account). `requireAuth` does its user lookup outside the `jwt.verify` try for that reason, so a database error is a 500. A future "wrong current password" check must not answer 401. It would sign the learner out.

Backend layout (`backend/src/`): `app.js` (Express app), `routes/` (`auth.js`, `content.js`, `progress.js`, `admin.js` — admin routes require the ADMIN role), `lib/auth.js` (JWT + middleware), `lib/progressSummary.js` (server mirror of the frontend's per-module progress math — keep the two in sync). Response shapes intentionally match what the old localStorage implementation returned (e.g. `{ part }`, `{ deleted: true }`, part details keyed by id).

**Content** (the equipment row, modules, hotspots, hotspot categories, checklist items, quiz questions, users) lives in PostgreSQL (`backend/prisma/schema.prisma`).

**Draft/publish applies to `Course` and `Hotspot`**: the columns are the published row a learner sees and `draft` holds the admin's pending edit as a whole payload, null when nothing is pending. Every learner-facing reader in `routes/content.js` therefore **selects columns explicitly** (via the serializers in `lib/hotspots.js` / `lib/courses.js`) rather than returning the row — a `findMany` with no `select` would ship the draft to learners. `Module`, `Equipment`, `ChecklistItem`, `QuizQuestion` and `HotspotCategory` still save immediately; they are short labels with no long-form body to get caught half-written.

**There is one hotspot table.** `Hotspot` holds every marker on the model — one row per physical component — and `inParts` / `inWalkAround` say which surfaces show it. It replaced four tables (`Part`, `PartDetail`, `WalkAroundHotspot`, `EquipmentHotspot`, merged in `20260814090000_merge_hotspot_tables`) that each kept their own copy of the same components: the forklift's mast, forks, tires, lift chain, overhead guard and counterweight existed as *both* a `Part` row and a `WalkAroundHotspot` row, so moving a marker moved it on one surface only. Do not reintroduce a per-surface hotspot table.

Fields group by the surface that reads them: always (`label`, `position`, `sortOrder`, plus the `title`/`subtitle`/`image`/`description` detail card every surface renders), parts-only (`category` — the filter chip — `functionText`, `inspectionReminder`, `safetyNote`, `relatedModule`, `checklist`), walk-around-only (`inspectCategory`, `state`, `inspect`, `safeFeedback`, `unsafeFeedback`, `unsafeScenarios`). **`category` and `inspectCategory` are deliberately separate columns**: the mast is "Load Handling Parts" to identify but "Exterior condition" to inspect. `state` is the engine phase a marker belongs to and **empty means every phase**. A row with a null `position` and neither surface flag is a detail card with no marker.

Learner progress (`parts.viewedPartIds`) and walk-around step data (`Course.data.checks[].hotspot`) reference hotspot ids bare, so an id is fixed at creation: the create endpoint slugs the label and refuses a clash (409) rather than renaming. Defaults are code — `data/hotspotDefaults.js` composes `partsData.js`, `viewerHotspots.js` and `inspectionScenarios.js` into the merged rows — so `builtIn` rows can be reset to them.

One endpoint set serves every surface: `GET /api/content/hotspots[?surface=parts|walk-around]`, `GET /api/content/hotspot-details` (keyed by id, includes marker-less cards), `GET /api/content/hotspot-categories`, and `/api/admin/hotspots` for CRUD + publish/revert/reset/reorder. The frontend seam is `getHotspots(surface)` / `getHotspotDetails()` / `getHotspotCategories()` and the `adminListHotspots`-family; one admin component, `components/admin/HotspotAdmin.jsx`, takes a `surface` prop that scopes its list and sets a new row's default flags.

**The `Equipment` row** holds the forklift's admin-editable configuration: `title` (what every `{equipment}` token resolves to), `imageUrl` (the hub plate artwork), `content` (hub copy) and `simConfig` (driving overrides). `prisma/seed.js` creates it create-if-missing from `EQUIPMENT_DEFAULTS` in `data/equipment.js`, and the backend addresses it through `EQUIPMENT_ID` / `findEquipment()` in `backend/src/lib/equipment.js`. `GET /api/content/equipment` returns it as one object (404 if unseeded) and `PATCH /api/admin/equipment` updates it; the frontend seam is `getEquipment()` / `adminUpdateEquipment(payload)`.

**The 3D model is code, not content.** `EQUIPMENT_MODEL_URL` (`data/equipment.js`) is forklift.glb, and every viewer loads it directly: the driving scene, the parked `vehicle` decoration, `HotspotViewer` and `PartsViewport`. Hotspot positions, rig node names, the collision footprint and the seat are all measured against that file at its authored origin and 1x scale, so there is no admin model URL, scale or height offset, and nothing fits or rescales a model.

**The vehicle profile lives on `Equipment.simConfig`** (JSON, overrides only, same rule as `content` below): the body footprint half-extents used for cone/wall/rack/pallet collision and the first-person seat (`rig.cabin.seatOffset`), edited under Equipment Settings (`components/admin/VehicleProfileEditor.jsx`). `keyLegend` and `failMessages` overrides are still honoured though nothing edits them. Defaults are code — `data/vehicleProfile.js`, measured from forklift.glb — and `lib/vehicleProfile.js` builds the profile **key by key** over them rather than spreading the row, so keys a row kept from the multi-equipment era (`modelUrl`, `parkedModelUrl`, `hasForks`, rig node names) have no effect; the editor also drops them on the next save. The wheel/mast/carriage node names and the mast foot come from `DEFAULT_RIG` only. Forks are always present: there is no `hasForks`, and the HUD always shows R/F/T/G.

**Hub copy lives on `Equipment.content`** (a JSON column, no draft — same reasoning as above). It holds *only the keys an admin overrode*; the defaults are code, in `frontend/src/data/hubContent.js` (`HUB_CONTENT_FIELDS` — key, label, section, optional `multiline`, and a `default(context)` builder). `lib/hubContent.js` resolves a row against those defaults: a blank or missing override falls back to the default, and `{equipment}` / `{learner}` tokens are substituted. So improving a default still reaches every field an admin never overrode, and clearing a field in the admin's **Hub Content** panel (`components/admin/HubContentEditor.jsx`) restores stock copy — the PATCH route drops blank keys rather than storing them. Add new hub copy by adding a field to `HUB_CONTENT_FIELDS` and reading `copy.<key>` in the page; no migration. Write defaults with the `{equipment}` token rather than the literal name, so renaming the equipment in Equipment Settings reaches them.

The database is seeded from `frontend/src/data/*.js` by `backend/prisma/seed.js` — those files stay the single source of defaults, so backend seeding imports them directly (which is why `data/` files use explicit `.js` import extensions; keep doing that). Driving-course geometry is also in the DB (`Course`, see below). What still deliberately stays in `frontend/src/data/` is the rest of the 3D/simulation config: hotspot coordinates, scenario scripts, and device effects.

**Module steps** (`Course` table) hold one row per step of Modules 2-4 — *every* step, not just the driving ones. `kind` picks how the page renders the row:

- `briefing` — reference image + markdown (`content`: `image`, `sceneBody`, `body`, `showSyllabus`, `syllabus`, `objectives`)
- `driving` — the WASD course `DrivingSimulationViewer` runs (`data`: `start`, `checkpoints`, `decorations`, `pallets`, `dropZone`, `parkingBay`, `capacityKg`, `failConditions`). `capacityKg` is the truck's capacity plate (blank is the reference 2,270 kg, `resolveCapacityKg()`), and `failConditions` holds `{ overload, loadDrop, highTravel }`; read it through `resolveFailConditions()` in `lib/courseGoals.js`, which maps the pre-physics keys (`suddenStop` / `sharpTurn` / `unsecuredTravel`) onto `loadDrop`. The Course Editor writes only those three.
- `activity` — a React activity keyed by `content.activityId` (`shutdown-sequence`, `reporting`). Admins can reorder or delete these but not create them, since the screen is code; the create endpoint refuses the kind. The screen's **content is editable**: the shutdown cards (`content.actions` with their `order`, plus the `displayOrder` scramble) and the reporting prompts (`content.prompts` with `shouldReport`, `feedback`, `wrongFeedback`) all live on the row, edited via `components/admin/ActivityContentFields.jsx`.
- `walk-around` — an inspection phase, set by `data.phase`: `engine-off` (click every check card or 3D marker, then start the engine when `requireEngineStart`), `engine-on` (judge every `gauges` reading correctly and run every `devices` test) or `defect-test` (answer every `scenarios` question correctly). Each phase is its own row, so a module can have any subset in any order, and all three are graded step ids. Rendered by `components/WalkAroundStep.jsx` with the grading in `lib/walkAroundStep.js`; markers come from `hooks/useInspectionHotspots.js`, which fetches the `inWalkAround` hotspots; a marker's `state` picks the phase it shows in, and an empty one shows in every phase. They are placed **inside the Walk Around step's own panel** in the Module Editor, beside the checks that reference them — the same `HotspotAdmin` Parts Identification uses, with `surface="walk-around"`. A marker ticked for both surfaces is one row edited in either place, not a copy.
- `checklist` / `quiz` — render the **module's** `ChecklistItem` / `QuizQuestion` rows, which are edited in their own dashboard tabs rather than on the step; the row only carries intro copy. Both are ungraded and never gate Next. `components/ModuleChecklistStep.jsx` holds all three exports.
- `summary` — the auto-built completion grid plus editable copy (`content`: `body`, `completeMessage`, `incompleteMessage`, `counters`, `nextRoute`)

  `nextRoute` is a key, resolved by `resolveNextRoute()` in `lib/moduleContent.js`: `hub` / `modules` / `parts` / `assessment` become those training pages, `module:<slug>` becomes that module, and anything else resolves to null, so Submit falls back to the module's built-in destination. The admin picker offers the four fixed targets plus one entry per existing module.

Two things a step row owns are *module*-wide rather than step-wide, because the module has exactly one of each row and no editable module record to hang them on: the briefing carries the `objectives` shown in the shell's sidebar on **every** step plus the `syllabus` card values, and the summary carries `nextRoute` — a key, not a path, of the scheme in `lib/moduleContent.js`, where Submit sends the learner. `lib/moduleContent.js` is the reader for all three; each falls back to the static `data/trainingModules.js` value (or the page's own fallback route key) so a row seeded before the field existed behaves exactly as it did. `prisma/seed.js` backfills content keys that are missing from a built-in row for the same reason — keys the row already has, including ones an admin blanked, always win. In a driving row's `data` it backfills only the safety signs' settings (`COURSE_ALERT_KEYS`: `speedLimitKmh`, `alerts`, via `withMissingAlertDefaults()` in `lib/courseAlerts.js`), into the pending draft too, which is how a stock speed limit reaches a deployed database; geometry is never backfilled. A stock value only gets that far if `normalizeCourseGeometry()` (`data/courseDefaults.js`) passes its key through, so a new key in `data/drivingCourse.js` needs adding there.

Row columns are the *published* version; `draft` holds the admin's unpublished edit as a whole payload, so a half-finished step never reaches a learner. Defaults come from `data/courseDefaults.js`, which composes `moduleScenarios.js` (step order + text), `drivingCourse.js` (geometry) and `trainingModules.js` (lesson text) — those stay the baseline that "Reset to default" restores, so keep editing them for stock content.

A row's `id` doubles as the step id learner progress is keyed on; renaming one orphans that progress, which is why the dashboard does not offer it. Briefing and summary ids are namespaced (`load-handling-briefing`) because every module has one and `id` is the primary key; driving and activity ids stay bare.

**There is one quiz system.** `QuizQuestion` holds every question in the app; `context` says which kind — `'module'` (a module's quiz step, `moduleId` set) or `'parts'` (the Parts Identification quiz, `moduleId` null). `options` is an array of plain strings and `answer` is one of them. The old `PracticeQuestion` table was merged in (migration `20260814020000_merge_practice_into_quiz_questions`) — do not reintroduce a separate "practice quiz" concept, in the code or in UI copy.

One endpoint serves both: `GET /api/content/quizzes?module=<slug>` or `?context=parts`, and `POST /api/content/quizzes/submit` with the same scope in the body. The frontend seam is `getQuizQuestions(scope)` / `submitQuiz(scope, answers)` and one learner component, `components/Quiz.jsx`, which takes that same `scope` object (`{ module }` or `{ context: 'parts' }`). Admin edits both kinds in `components/admin/QuizAdmin.jsx` (Quizzes tab) — questions save immediately, with no draft/publish step.

**Quizzes are graded on the server.** The GET deliberately omits `answer`; the client posts its choices to `/submit`, `lib/grading.js` scores them, writes the attempt into the learner's `ProgressSnapshot`, and returns the score plus per-question feedback. The client then calls `hydrateProgressFromServer()` so its next debounced push carries the attempt instead of overwriting it. There is no client-side scoring left — `recordQuizAttempt` / `recordPartsPracticeAttempt` were removed rather than left unused.

Where an attempt lands: module quizzes go to `progress.quizzes[moduleSlug]`, parts quizzes to `progress.parts.quizAttempts` (newest first). Two older shapes may still arrive from a stale tab or a client's localStorage — `parts.quizzes[equipmentId]` (before migration `20260929120000_forklift_only` flattened it) and `parts.practiceAttempts` (before `20260814100000`). `migrateParts()` (`lib/migrateParts.js`, run by `progressService.js`, `lib/grading.js` and `lib/progressSummary.js`) folds the forklift's list and the legacy one into `quizAttempts` and drops any other equipment's, so the old keys disappear on the next write. `PUT /api/progress` stores the client payload as-is, which is why every server-side reader of `parts` goes through it. `getPartsQuizAttempts()` / `getLatestQuizAttempt()` in `progressService.js` are the readers; don't read the key directly.

Because the pages import `equipmentUsageModules` and `partsHotspots`, anything nested in those files ships in the browser bundle. The answer keys therefore live in **`data/moduleQuizzes.js`** and **`data/partsQuizzes.js`**, which only `prisma/seed.js` imports. Keep it that way: re-exporting either through `lib/trainingData.js`, or adding a static fallback that imports them, puts the answers back in the bundle. `npm run build` then `grep -rl "<a known answer>" dist/assets/*.js` is the check.

**Progress** is per-user in the DB (`ProgressSnapshot`, one JSON document per user, same shape as the old localStorage copy). `lib/progressService.js` still keeps localStorage (`gearview_progress_v1`) as the synchronous read source: it hydrates from `GET /api/progress` on login/session restore (`hydrateProgressFromServer()`, called in `App.jsx`), pushes debounced `PUT /api/progress` on every change, and clears only the local copy on logout. Changes dispatch a `gearview-progress-change` custom event; `hooks/useProgress.js` subscribes to keep React state in sync.

### Routing — hand-rolled, no react-router
`frontend/src/lib/router.js` defines a flat `routes` map (path strings), `moduleRoute(slug)`, and a `goTo()`/`normalizePath()` pair that push/replace `window.history` state and dispatch `popstate`. `App.jsx` is the only router: it holds `path` state synced to `popstate`. The training pages are `/training` (hub), `/training/modules[/<slug>]`, `/training/parts` and `/training/assessment`; `App.jsx` parses `/training[/section[/slug]]` and renders NotFound for anything else. URLs from before the forklift-only change (`/catalog`, `/training/forklift/...`, `/training/forklift/equipment/...`) are mapped by the pure `legacyRedirect(path)` (tested in `lib/router.test.js`) and redirected in an `App.jsx` effect. Auth gating (redirect to `/login` if logged out, redirect to `/training` — the app's home screen — if logged in and on `/` or `/login`) also lives in `App.jsx`. Admin routes (`/admin`, `/admin/*`) are gated on `user.role === 'ADMIN'` and forwarded into `AdminDashboard`, which does its own sub-routing on the raw `path` prop.

### Home screen and training module flow
`TrainingHubPage.jsx` (`/training`) is the app's home screen — logging in, landing on `/`, and clicking the header brand mark all route here. It lists **sections, not modules**: hero + overall progress + a Training Modules card (averaged module progress, opens `/training/modules`) + a Parts Identification card (shown once there is a published `inParts` hotspot) + the final Assessment link. All of its copy comes from `resolveHubContent()` (`Equipment.content` over the defaults in `data/hubContent.js`), so don't inline new strings here. The old `/catalog` equipment grid (`ModulesPage.jsx`) was deleted.

`ModuleListPage.jsx` (`/training/modules`) is the module picker one level below the hub — one card per `Module` row (fetched via `getTrainingModules()`), each opening `/training/modules/:slug`. Its card CSS is prefixed `module-list-` for historical reasons.

`GenericModulePage.jsx` is the one module page for **every** module — the Walk-Around Check included, since Phase E turned it into `walk-around` step rows. It renders whatever typed step rows the module has — `hooks/useModuleCourses.js` fetches them and the page switches on each row's `kind` (briefing / driving / walk-around / checklist / quiz / activity / summary) in `renderScene`/`renderTask`, all inside `components/ModuleSimulationShell.jsx` (objectives / step list / hint panel / center scene / current-task panel / progress bar). Briefings render via `components/ModuleBriefing.jsx`, summaries via `components/ModuleSummary.jsx`, and the two built-in activities via `components/ModuleActivities.jsx` (ids listed in `lib/activitySteps.js`). Pages must not render `ModuleSimulationShell` until `useModuleCourses` reports `loading: false`, because completion percentage is computed against the graded step list.

`PartsIdentificationPage.jsx` (`/training/parts`) is the parts page: category groups over the `inParts` hotspots, the model beside them, and the shared `components/PartDetailCard.jsx`. The quiz step only appears once there are `context: 'parts'` questions. `HotspotIdentificationPage.jsx` was deleted when the hotspot tables merged — there is no second parts page.

`GenericAssessmentPage.jsx` serves `/training/assessment`: module progress, the parts markers and the parts quiz, all read from the database rows. "Generic" in its name and `GenericModulePage`'s means generic across modules.

Static seed content (steps, scenarios, checklists, quiz questions) is defined in `frontend/src/data/*.js` and re-exported through `lib/trainingData.js` — add new stock content there rather than inlining it in page components.

`ScopeNoticeModal` is deliberately *not* admin-editable — it is the "preparatory learning only, not a certification simulator" disclaimer (`scope.body`, which names the Class V forklift), shown as a dismiss-to-continue modal rather than inline content. It takes only `onDismiss`. It deliberately fires only where a learner is about to *start* a module-shaped activity — `GenericModulePage.jsx` (on mount, before the briefing renders) and `PartsIdentificationPage.jsx` (on mount, before the explore task renders) — not on the hub, module list, or assessment review, so it reads once per activity instead of on every screen. Each page owns its own `showScopeNotice` state; there is no cross-visit persistence, so it reappears every time the learner re-enters that module or the parts page.

The default task copy for a driving step - `courseTaskKey(course)` in `lib/courseGoals.js` - picks a key by the course's goal type. It returns `{ key, values }` rather than a sentence, because **the backend imports this file** (`backend/src/lib/courses.js`, for `validateCourse`) and must not pull the i18n catalog into the Node process; the caller translates.

Progress percentage per module is computed in `progressService.js` (`getModuleProgress`): simulation-reported percentage takes priority if present, otherwise it's derived from checklist completion averaged with the latest quiz score.

**`getProgressSummary()` is not keyed by module.** It returns only `raw`, `viewedParts`, `quizAttempts` and `simulations`. Per-module progress, per-module checklist completion and the parts/overall percentages all need the module slugs or hotspot ids the page is showing, so they are functions the page calls — `getModuleProgress` / `getChecklistCompletion` / `getPartsProgress` / `getOverallProgress` — not fields. They used to be prebuilt maps keyed off a hardcoded four-slug list, which is why every admin-created module reported "no checklist items" on the assessment page whatever it had. Don't put them back.

**Percentage denominators.** `checklistCounts` is cached in localStorage and refreshed by `hydrateChecklistCounts()`, because `getChecklistCompletion` is synchronous; it runs from its **own mount effect in `App.jsx`, not the session-restore effect** — that one early-returns whenever localStorage already holds the user, so a count hung off it would only refresh on an explicit sign-in. Its numerator is clamped to the denominator, because a checklist item an admin deleted stays in the learner's saved progress.

There is no equivalent hotspot cache: `getPartsProgress(progress, hotspotIds, hasQuiz)` and `getOverallProgress(progress, moduleSlugs, partsPercentage)` take the ids from the caller, which has already fetched them to render the page. `getProgressSummary()` therefore has no `parts` field.

Within a simulation module, per-step completion is a step-id map (`simulations[slug].stepsComplete`), built by `lib/simulationProgress.js` (`buildSimulationState`) — not a fixed list of named booleans — so steps an admin adds or removes are graded without a code change. The percentage is always recomputed against the module's *current* graded step list; entries left by a deleted step are ignored but never pruned, so re-adding the step restores completion. There used to be a `lib/legacyStepFields.js` migrating snapshots saved before `stepsComplete` existed (including a hardcoded `w`/`a`/`s`/`d` default for every `goalType: 'free'` driving step); it was removed, so any progress saved before that migration existed is no longer read.

A `goalType: 'free'` driving course (no checkpoints, bay or pallet to complete against — see `courseGoalType()` in `lib/courseGoals.js`) has no built-in completion rule at all: it **requires** `data.completionCode`, a JS expression an admin writes in the Module Editor's Goal section, checked at publish time (`validateCourse()`, which the backend also imports so an uncompletable free course cannot be published — the check only *compiles* the code via `new Function()`, never calls it, since this file also runs inside the Node backend process). Learner-side, `lib/customCompletion.js` evaluates it in a dedicated Web Worker (`lib/freeCompletionWorker.js`) rather than on the page — no DOM, no `localStorage`, so the code can't reach the learner's JWT — given only `{ keysUsed, engineStarted, seatbelt, parkingBrake }` (the last two are the cab switches' *current* positions, from the viewer's `cab-switch` event; `hooks/useDrivingController.jsx` re-evaluates when either moves), under a short timeout that `terminate()`s a hung rule. `GenericModulePage.jsx`'s `saveFreePractice` awaits the result and writes completion against the *stored* simulation snapshot, not the one its render closed over, same reasoning as `savePhase`'s `liveSimulation()`.

#### Part details system (shared by walk-around steps and Parts Identification)
Clicking a part/hotspot anywhere shows the standard detail card: `components/PartDetailCard.jsx` (reference image slot + title + subtitle + **markdown** description + optional status line). Markdown is rendered by `components/MarkdownContent.jsx` (react-markdown) — bullet points, numbered lists, bold, and inline images (`![alt](/images/x.png)`) anywhere in the description.

Detail content is **columns on the `Hotspot` row** (`title`, `subtitle`, `image`, `description`), so a marker carries its card with it and both surfaces show the same one. `getHotspotDetails()` returns them as an object keyed by id — including rows with no marker, which is why it is a separate call from `getHotspots()`. Seed defaults come from `data/hotspotDefaults.js`, which composes the markdown from `partsData.js`, `inspectionScenarios.js` and `viewerHotspots.js`. Admins edit them in the Detail card section of `HotspotAdmin`.

Consumers:
- `ModuleSimulationShell` "Current Task" panel renders `PartDetailCard` from `selectedDetail`/`onClearDetail` props; `GenericModulePage` builds `selectedDetail` for walk-around steps by overlaying `partDetails[id]` on the step row's own check/device entry, which supplies the context-specific status and feedback line. Auto-clears on Next/Back.
- `PartsIdentificationPage` builds `selectedDetail` straight off the clicked hotspot row, since the card fields are columns on it; `ModuleSimulationShell` renders it in the same panel.

To change what a part shows, edit the seed sources `data/hotspotDefaults.js` composes (or the admin dashboard for local overrides), not the components.

### 3D viewers
Three.js is used via `@react-three/fiber`/`@react-three/drei`, with `.glb` models served from `frontend/public/models/`. There are several distinct viewer components, not one shared abstraction — check which one a page already uses before adding a new one:
- `components/HotspotViewer.jsx` — the hotspot/marker viewer: walk-around steps and the admin placement stage (`adminEditMode`, device effects, defect overlays). Always loads `EQUIPMENT_MODEL_URL`.
- `components/DrivingSimulationViewer.jsx` — the WASD driving/obstacle-course scene. Its `course` prop comes from the `Course` table via `getModuleCourses()` (`data/drivingCourse.js` only supplies the seed/reset baseline) and its `profile` prop from `resolveVehicleProfile(equipment)` over the `Equipment` row.
  **The driving simulation is a headless core, not a frame loop over refs.** `lib/driving/simCore.js` owns one attempt: a plain `SimState` (`simState.js` — truck pose/speed/steer/engine, fork height and tilt, tip, stability margins, per-pallet pose and state, cones, parking, HUD fields) and the ordered pipeline `stepDrive` → `stepCollisionBody` → `stepForks` → `stepFail` → `stepPhysics` → `stepCollisionHazards` → `stepCheckpoints` → `stepPallet` → `stepStability` → `stepParking`. Steps read and write only `state` and the course-derived `world` (`stepPhysics` also the physics world, below), raise plain events on `state.events` (drained by `core.drainEvents()`), and **never touch three.js objects**. `syncView.js` is the one place state is copied onto the scene (truck group, tip pivot, rig nodes, pallets, cones), interpolating between the last two steps; `stepCamera.js` is a view step after it. The viewer drives the core from `useFrame` through `simLoop.js`, a fixed 1/60 s step (max 4 per frame), so 60 Hz and 144 Hz screens get the same sim. The carriage pose comes from the pure `forkPose(state)` over the measured constants in `rigGeometry.js`, not from the `Lift_Carriage` node — re-measure those if forklift.glb is re-exported (the viewer warns in dev on a mismatch). Pallet and cone poses are three.js `Vector3`/`Quaternion` *maths* values, which is fine under Node.

  **The hybrid physics model (Phase 7): the truck is driven by the steps' own model; what it carries, pushes and knocks over is Rapier's.** `lib/physics/world.js` (`createPhysicsWorld`) holds the bodies: the truck's box and the fork carriage (two tines and the load backrest) are *kinematic*, each pallet (one compound body with its load, fork pockets open) and each cone is *dynamic*, and the floor, racking (end posts, beams, decking), walls and parked vehicles are *fixed*. `colliders.js` builds the shapes from the measured data in `data/physicsProfile.js`. The world knows nothing about `SimState`: `lib/driving/stepPhysics.js` is the only step that talks to it. It moves the truck there, steps, and reads each pallet's and cone's pose and contacts back into state (`pallet.touch`, `pallet.slipSpeed`, `state.limits`, `frame.impacts`). Everything after it, and every reader (safety rules, audio, view, telemetry), reads state. Don't reach into the physics world from anywhere else.

  - **A load is not scripted.** It lifts because the forks are under it, stays by friction, slides under braking, and is set down by levelling the mast and lowering it. `lib/physics/palletState.js` (pure) derives `ground` / `carried` (with `landed`) / `settling` / `released` / `delivered` / `falling` / `dropped` from the contacts, and `stepPallet.js` turns that into the unchanged `pallet-lifted` / `pallet-dropped` / `pallet-delivered` events. `lib/loadPhysics.js` is now only the grip lamp's reading (`evaluateForkEngagement`, `forkGrip`). Don't bring back a pinned carry, a snap to the rack's centre or a slip gain.
  - **The forks are solid against what doesn't move**: they stop at the floor (`tineClearance()` in `forkPose.js`), and they and a load on them stop against racking, walls and parked vehicles through `state.limits`, which `stepPhysics` reads off one step's contacts and `stepCollisionBody` / `stepForks` apply on the next. The truck's *body* against racking and walls is still the 2D test in `lib/simCollision.js`, which the backend's course validator shares. Pallets and cones don't block the truck; it pushes them.
  - **Stability is analytic, not Rapier.** `lib/physics/stability.js` (pure, kilograms and metres) gives a forward and a sideways margin from the carried pallet's real centre of gravity, the braking and the turn; `stepStability.js` fails the attempt as `tip-over` once a margin has been negative for 0.25 s, and `stepFail` animates the fall (`tipMatrix()` in `forkPose.js`: a pitch onto the fork tips, or a roll about a side of the stability triangle). The truck's figures are `STABILITY_DEFAULTS` in `data/vehicleProfile.js`; its centre of gravity is derived from the rating, and `stability.test.js` pins that the rated load holds and 115% does not. `lib/physics/loadChart.js` derates the capacity by load centre; the overload fail, the overload sign and the dashboard's capacity plate all read it through `state.load`.
  - **Always-on fails:** cone, wall, vehicle, rack, `pallet-impact` (the body or forks striking a pallet at over 5 km/h along the line of contact) and `tip-over`. Per course: `overload`, `loadDrop`, `highTravel`.
  - **Rapier has to be loaded before a core exists.** `createSimCore()` is synchronous and reads `loadedRapier()`; the viewer awaits `loadRapier()` before it mounts an attempt, and a test imports `test-helpers/physics.js`. The core builds its world on the first `step()` and frees it in `dispose()`, which the viewer calls a tick after unmount (so React's development double-mount cancels it). A test that builds a core should dispose it.
  - Rapier is deterministic for the same inputs on the same build, which is why the characterization trace can compare pallet poses (rounded to 1e-5).

  Input is the normalised operator model in `lib/driving/controls.js` (`throttle`/`brake`/`inching`/`steer`/`direction` F-N-R/`lift`/`tilt`/...), combined across sources by `mergeControls()`. `keyboardSource.js` is the keyboard source (W = throttle in F, S = brake then throttle in R, with the old key priorities); `hooks/useDrivingInput.js` just feeds it window key events. Free-practice `keysUsed` still gets the old letters: `createKeyActiveTracker()` reports them from the merged controls (`legacyKeysFromControls`) plus the source's own presses, so a future wheel source keeps completion code working. The HUD reads the telemetry store (`lib/driving/telemetry.js` + `hooks/useTelemetry.js(store, selector)`), published at 15 Hz and on every sim event — don't add per-frame `setState` to the viewer. The viewer maps core events onto its unchanged `onEvent` vocabulary (`engine-on/off`, `key-active`, `checkpoint`, `course-complete`, `pallet-*`, `parking-complete`, `sim-failed`), plus `cab-switch` and `safety-tally`. `window.__drivingDebug` / `__drivingDebugSet` (DEV only) are `core.debugSnapshot()` / `core.debugSet()`.

  **Parity is tested.** `lib/driving/__golden__/characterization.json` is a trace of 28 scripted drives (`test-helpers/drivingScenarios.js`, run on the headless adapter in `test-helpers/headlessDrive.js`, covering every built-in course, each fail, the Phase 4 interlock and lever and the Phase 7 physics), first recorded from the pre-refactor sim and re-recorded on purpose in Phase 4 and again in Phase 7; `simCore.characterization.test.js` replays them through the keyboard and dashboard sources and the fixed-step loop and must match. `lib/driving/physicsScenarios.test.js` judges the same drives on what the physics was supposed to do, and drives every built-in course to completion. A deliberate behaviour change must replace the golden file in the same commit and say why — `RECORD_GOLDEN=1 RECORD_REASON="..."`, which writes the reason into the file — never regenerate it to make a failing refactor pass. Scenarios start the engine through the interlock (`startEngine` / `shutDown` phases, `cab` switch settings).

  **The cockpit (Phase 3) is view-side.** `lib/driving/cameraModes.js` is the camera: a pure state machine (`cameraReducer`) over two views, first-person (default) and chase, plus the admin free camera. The commands `cameraToggle` and `cameraLeft/Right/Up/Down` come from C and the arrow keys, the wheel's D-pad and the HUD buttons alike. In chase, left/right step four orbit stops (behind, left, front, right; behind is mouse-orbitable) and up toggles overhead; in first-person they glance round a 60° ring, eased by `stepCamera` through `glanceRef`. `cameraPose()` turns the state into a pose. Keep `camera.up` at +Y: drei's OrbitControls reads it once at mount, so overhead gets heading-up from a tiny back offset instead. `lib/driving/proximity.js` is the per-sector nearest-obstacle query over the collision rects (body plus forks), using `rectRectDistance()` from `lib/simCollision.js`; the safety rules read it too, plus `pathClearance()`, what lies in the straight path the truck sweeps (`forwardGap()` in `simCollision.js`). `components/driving/ProximityInset.jsx` draws the inset as a second render pass in the same canvas: its `InsetRenderer` is a render-priority `useFrame` that **takes over rendering** (main camera, then the inset into the HTML frame's box), so don't add another priority frame loop. `components/driving/OperatorDashboard.jsx` reads the telemetry snapshot built by `lib/driving/cockpitTelemetry.js` and writes through `lib/driving/dashboardSource.js` (key switch, direction lever, seatbelt, parking brake, lights); the keyboard's E/B/Space/H (and the wheel's buttons) are commands the viewer routes to the same switches, and camera/inset keys are view commands. The dashboard's key START only *asks* (`engineStart`): the core decides. Fuel, temperature and hours (`lib/driving/cabGauges.js`) are illustrative and view-side. forklift.glb has a `Steering_Wheel` node, split out of `Forklift_Body` by `frontend/scripts/split-steering-wheel.mjs`; its pivot and the lift/tilt lever pivots are constants in `DEFAULT_RIG`, `buildVehicleRig()` builds the pivot groups, and `syncView` turns them. Edit forklift.glb surgically like that script does, not by a Blender round trip, which rebuilds the skin and hierarchy the rig and hotspots depend on.

  **Controls and the drive model (Phase 4).** The engine starts only through the pre-start interlock (`lib/driving/interlock.js`: seatbelt, parking brake, direction N); `simCore` refuses `engineStart` with an `engine-blocked` event and `state.interlock`, and `cockpitSnapshot`'s `need*` flags ring the unmet controls. `stepDrive` is the drive train (`driveSpeed()`: throttle to a target speed in the lever's direction, N only revs, brake up to 0.5 g, inching, the parking brake holding the truck) and a rear-wheel-steer bicycle model about the front axle (`frontAxleZ`/`rearAxleZ` in `rigGeometry.js`, 80° lock). It writes `nextHeading` with `nextX/nextZ`, and `stepCollisionBody` commits all three or none. Constants are real units in `constants.js`, from the Toyota 8FGU25's public spec listing or labelled GearView defaults. The keyboard steers a rate-limited virtual wheel whose lock shrinks with speed (`keyboardSteerLimit()`). The parking goal wants N and the parking brake before engine off.

  **Wheel, pedals, shifter (Phase 4).** `lib/driving/gamepad.js` is pure (ids keyed by `vendor:product`, `decodeHat`, axis normalisation, capture, the action list, `resolveControllerConfig()` and the shipped T300 RS `044f:b66e` / TH8A `044f:b660` defaults). `wheelSource.js` turns a pad snapshot into operator controls and commands; the viewer polls `gamepadBrowser.js` once per frame and merges `[wheel, keyboard, dashboard]`, wheel first, so a shifter's lever wins. Config lives in localStorage (`controllerStore.js`, `gearview_controller_v1`, a change event), never the DB: it is this machine's hardware. `components/driving/ControllerSetup.jsx` (from the HUD and the hub) edits it through the pure `lib/driving/controllerSetup.js`. Never hardcode an axis or button index outside `defaultControllerConfig()`. A plugged-in wheel is live in any browser on the machine, including Playwright's, so a resting wheel steers; the sim-verify runner hides gamepads for keyboard scenarios.

  **Safety rules and signs (Phase 6) read the simulation and never change it**, like the audio, so the characterization trace cannot depend on them. `data/safetyThresholds.js` holds every threshold in real units, each a GearView default labelled with the OSHA 1910.178 paragraph it implements (OSHA gives no numbers). `lib/driving/safetyRules.js` is the rule table (`{ id, severity, kind, pictogram, messageKey, sound, osha, when(snapshot) }`; `when` may return an override, which is how obstacle-ahead becomes a stop sign) and the pure alert-queue reducer: a sign comes up after its rule has held 150 ms, clears 500 ms after it stops, danger first, at most two, and `edges` are what began this step. `safetySnapshot.js` builds what the rules read from `SimState`, `proximity.js` and the view (look direction, the course's speed limit); `safetyMonitor.js` is one attempt's watch, which the viewer calls once per frame and the tests once per step. `components/driving/SafetySigns.jsx` draws the queue's `shown` list from its own telemetry store: ISO 7010 frames (yellow triangle, blue disc, red ring) with our own pictograms and `safety.*` i18n text, in `.driving-hud-upper`, the row above the dashboard it shares with the proximity inset. They are laid out, not overlaid, so keep them in that row rather than positioning them absolutely. Caution and danger play `cautionChime` / `dangerAlarm` (`alertSounds()` in `drivingAudio.js`).

  `lib/courseAlerts.js` (pure, backend-safe, imported by `courseGoals.js`) lists the rule ids with `essential` and the Course Editor's labels, and reads what a course stores: `course.data.alerts` holds `{ ruleId: false }` for switched-off rules only, and `resolveAlerts()` ignores a stored `false` on an essential rule (obstacles, tail swing, overload, tip risk, load shifting, start interlock); `course.data.speedLimitKmh` defaults to 8. A rule with `hint: true` (`release-load`, "tilt the mast forward to set the load down", for a load lowered to where it is going with the mast still back) is shown like any other but is not a violation: the monitor leaves its edge out of the tally, and it has no `safety.rule.<id>` summary line. A new rule is a row in both files (a test keeps them in step), a threshold, a pictogram and `safety.sign.<id>` / `safety.rule.<id>` in both languages. The `forks-high-travel` sign and the `highTravel` fail share one value, `FORKS_TRAVEL_HEIGHT` (30 cm, the team's value once a load rode on physical forks), `overload` reads the load chart (`state.load.overCapacity`), and `tip-risk` and `load-shifting` read the stability margins and the load's slide along the tines, both essential. `sound-horn` is still a stretch goal. Changing a threshold that a fail shares changes the simulation: re-record the trace on purpose.

  **What the signs logged is saved per step.** The viewer raises `safety-tally` with the attempt's running `{ violations, dangers }` (an empty one when an attempt starts), and `hooks/useDrivingController.jsx` writes `simulations[slug].attemptStats[stepId] = { completedAt, violations, dangers, fails, bestViolations, failsSinceCompletion }` on completion. `lib/simulationProgress.js` owns that shape (`tallyAlert`, `withAttemptComplete`, `withAttemptFail`); `components/driving/AttemptSummary.jsx` shows it under a completed step. It is the evidence Phase 9's skills checklist will read, and it is client-reported like the rest of the progress snapshot.

  **Rapier is pinned.** `lib/physics/rapier.js` lazy-loads `@dimforge/rapier3d-compat` into its own 2.2 MB chunk, fetched when the first driving step mounts (it also runs under `node --test`). The package is **pinned to 0.19.3**: 0.20+ under-applies friction on a load the mast has tilted, and `lib/physics/world.test.js` fails if an upgrade brings that back, so read the Phase 2 results in the plan before bumping it. `data/physicsProfile.js` (pure, backend-safe, like `lib/physics/loadChart.js`) holds the world settings, the collider data measured off the fork, pallet, cone and rack models, and which pallet a load weight gets (`palletPhysics()`; the cement-bag pallet is drawn and collided a quarter turn round, so its open side faces the forks). To see what the physics simulates, the admin's 3D preview has a "Colliders" button (`world.debugRender()`).
- `components/PartsViewport.jsx` — the parts explore viewport `PartsIdentificationPage.jsx` uses (also always `EQUIPMENT_MODEL_URL`).

  The two share `components/viewer/ViewerShared.jsx` (`CameraFocus`, `ViewerLoadingPanel`, `ViewerErrorBoundary`) and `viewer/useClonedScene.js`. They are deliberately **not** one component: their scenes, material passes and interaction genuinely differ, and `HotspotViewer` builds its rig before the material pass, so only what was identical is shared.

**Both stand the model on the floor with drei's `<Center top cacheKey={EQUIPMENT_MODEL_URL}>`, and both need two things right to keep it there.** The floor is at y = 0 — don't reintroduce a negative floor constant to "fix" a float, because that lifts the markers too. And `HotspotViewer` builds its rig in a **layout** effect so `<Center>`'s measurement runs against the de-skinned meshes — forklift.glb's parts are rigidly bound `SkinnedMesh`es whose node transforms carry an offset that skinning cancels at render time, so a raw bbox reads ~0.65 units high. `<Center>` measures only when its `cacheKey` changes, which with a constant key means once at mount; the model never swaps, and the device-demo animations and wireframe toggle must not re-ground it.

### Audio
There is one audio system, and every sound is a recorded sample (Phase 5). `lib/audio/audioEngine.js` owns a single shared `AudioContext`: a master gain (the learner's volume and mute), four buses (`engine` / `machine` / `alerts` / `ui`), a fetch-and-decode cache, `playOneShot(name)` and `createLoop(name)`, whose handle has `setGain` / `setRate` / `stop`. **Gains and rates only ever move through `setTargetAtTime`**; setting an `AudioParam`'s value directly steps the signal and clicks. `createAudioEngine()` takes its context, loader and clock as arguments so `audioEngine.test.js` runs it against a fake context; `getAudioEngine()` is the app's shared one, and the only place that touches `window`. It replaced `lib/deviceAudio.js`, which synthesized three sounds on a private context. Don't add a second context or an oscillator.

`data/soundBank.js` is the bank: name to file, bus, gain and `loop`. It is code-owned, not admin-editable. The files are in `frontend/public/audio/` with `CREDITS.md` (source URL, author and licence per file; all CC0 from Freesound). `frontend/scripts/build-audio.mjs` builds them with ffmpeg from the originals in `frontend/audio-src/raw/` (gitignored), and its `SOUNDS` list is the record of every cut. **Loops are gapless mono FLAC, never MP3 or AAC**, whose encoder padding clicks at the loop point; one-shots are MP3. The bank's budget is 3 MB. Two values in the bank are measured from the built files and must be re-measured if the engine samples change: each engine loop's `firingHz` and the start recording's `catchAt`.

**Audio is view-side: it reads `SimState` and never writes it**, so the characterization trace cannot depend on it. `lib/driving/drivingAudio.js` holds the pure `audioTargets(state, { capacityKg, rev })` (the gain and rate each loop should head for; the engine's revs are `engineRevTarget(state)`, the throttle with a floor from road speed, which `createDrivingAudio` slews with `slewRev()` so they rise and fall like an engine's rather than flipping with a keyboard's all-or-nothing throttle: the two engine loops crossfaded at equal power and pitched to one firing frequency, the reverse beeper from the same `displayedDirection()` the dashboard shows, the pump whine, relief strain at the lift's end stops, the chain), `eventSounds(event)` and `switchSounds(previous, next)` for the one-shots, and `createDrivingAudio(engine)`, which the viewer builds in an effect per attempt and calls once per frame. `alertSounds(edges)` names the chime or alarm for the safety signs that came up. The core's `impact` events (`{ what, speed }`: a pallet struck, a load landing, a cone, structure) map to one-shots in `eventSounds()`, louder the harder (`impactGain()`), and `forkScrape` is a loop that sounds while the tines are on the floor and the truck moves. A name that is not in the bank plays nothing, which is how the three impact one-shots wait for their recordings.

Nothing loads until a surface asks: `DrivingSimulationViewer` preloads `DRIVING_SOUNDS` when it mounts, `hooks/useWalkAroundController.js` the device-test sounds (`engineOnDeviceEffects[].sound` names a bank entry; a loop plays for the effect's `duration`). The hub creates no context and fetches no sample; keep it that way. The engine never starts a source on a suspended context (everything queued would sound at once on resume), and a one-shot that could not start within 0.4 s is dropped. Browsers keep a context suspended until a user gesture, and gamepad input may not count, so the driving HUD shows "Click to enable sound" (`useAudioSuspended()`); the engine also suspends while the tab is hidden, where the frame loop that steers the loops isn't running.

Volume and mute are `lib/audio/audioSettings.js` (`gearview_audio_v1` in localStorage, wrapped in try/catch, with a change event, like `controllerStore.js`). Mute is global. `components/AudioControl.jsx` is the one control, on the operator dashboard and on the walk-around task panel, because the device tests have to be audible without visiting a driving step. Its slider blurs on pointer-up: `useDrivingInput` ignores keys while a form field has the focus. `window.__audioDebug()` (DEV only) is the engine's `debugSnapshot()`, which sim-verify's `sound` scenario reads.

### Admin dashboard
`AdminDashboard.jsx` reads/writes content through the same `lib/api.js` admin functions (`adminSaveHotspotDraft`, `adminUpdateModule`, `adminUpdateChecklistItem`, `adminUpdateQuizQuestion`, and their delete counterparts) and reports on progress via `adminListContent()`.

**Information architecture: Overview | Training Content | Users | Reports.** Training Content has three sections:

- **Modules** (`/admin/modules`) — `ModuleListAdmin.jsx`: every module in `sortOrder`, with Edit / Move up / Move down / Delete and an Add form. Reordering posts `/admin/modules/reorder` (`{ ids }`); creating posts `/admin/modules` (the slug is the slugified title), which also writes one blank briefing step so the module is never empty; deleting removes the module's `Course` rows too (they reference it by slug, not by relation, so nothing cascades for them).
- **Parts Identification** (`/admin/parts`) — `HotspotAdmin.jsx` with `surface="parts"`: the hotspot list beside the model (add / place / drag / publish / reset / delete), each row's detail card, and its parts fields. Every placed marker renders on the model, not just the selected one: clicking a marker selects that hotspot, dragging the selected one moves it. The list is scoped to the surface with a "Show N more not on this page" toggle for the rest, and each row is tagged with the surfaces it appears on. Beside it: part categories (`HotspotCategory`) and the parts quiz. Its `hotspot-*` classes still live in `WalkAroundHotspotAdmin.css`.
- **Equipment Settings** (`/admin/settings`) — `EquipmentCardEditor.jsx` (title and hub artwork image), the Hub Content field editor, and the **Driving Simulation** vehicle profile (footprint and seat). The hub-copy placeholders need to know whether there is a parts page, so `GET /api/admin/content` also sends `partsHotspotCount` — the same "published `inParts` hotspots" rule the hub uses.

There are no Checklists / Quizzes / Driving Courses tabs: those rows are edited **inside the module that renders them**.

#### Module Editor — `/admin/modules/:slug`
`components/admin/ModuleEditor.jsx` is everything one module owns: its card fields, its ordered step list (create with a kind picker, reorder, select), and the selected step edited in place. Step kinds are shown by learner-facing name — Read Up (briefing), Driving Course, Checklist, Quiz, Built-in Activity, Completion Summary. Checklist steps render `ChecklistAdmin.jsx` under the step's own fields and quiz steps render `QuizAdmin.jsx` scoped to that module, because those rows belong to the *module* — every checklist step of a module shows the same items. Course rows are fetched separately from `adminListContent()` (`adminListCourses()`) because the geometry blobs are large and only this screen needs them.
- `CourseEditor.jsx` — one step, rendered by the Module Editor. The panels are kind-aware: driving steps get the map, goal type, rated capacity and the three load-handling fail switches, and the Safety signs panel (speed limit, one switch per rule, essential rules locked on); briefings get the image URL + two markdown bodies + syllabus toggle; summaries get the copy and counter toggles; activities get a read-only note. Only driving steps are geometry-validated. Also holds save/publish/revert/reset/delete and the on-demand 3D preview (the same `DrivingSimulationViewer` the learner drives, mounted only when asked so selecting a step doesn't spin up a WebGL context). The preview drives with the learner's vehicle profile: `AdminDashboard` passes the `Equipment` row down through `ModuleEditor` as `equipment`, and `CourseEditor` resolves it, so a footprint or seat override shows in the preview.
- `CourseCanvas.jsx` — the SVG top-down map. It is drawn **from the driver's seat**: +Z (forward) runs up the screen and +X runs to the *left*, because at heading 0 the forklift faces +Z and steering right turns it toward -X. Keep that mapping or left/right on the map stops matching the simulation.
- `CourseInspector.jsx` / `CourseGeneratorTools.jsx` — per-object properties and the bulk cone layouts.
- `lib/courseEdit.js` — pure mutations over the geometry, addressing objects by a `"<list>:<index>"` key. The parked-obstacle decoration kind is `vehicle`; it was `forklift` until migration `20260814110000_rename_vehicle_decoration`, so read stored decorations through `decorationType()` rather than `entry.type`.
- `lib/courseGoals.js` — the four completion modes `DrivingSimulationViewer` implements (`checkpoints` / `parking` / `pallet` / `free`) plus `validateCourse()`, which the backend also imports so an unwinnable course cannot be published.
- `lib/courseGenerators.js` — `coneLine` / `corridorCones` / `coneBay` / `coneBox` / `slalomCones`, shared by `data/drivingCourse.js` and the editor's insert tools. Generator output is **baked** into the decorations list as loose cones, so every cone stays individually movable.

Edits save as a draft and only reach learners on Publish. Built-in courses keep their `data/courseDefaults.js` baseline and can be reset to it; admin-created ones cannot.

All admin edits persist to PostgreSQL through the API and are shared by every user — the dashboard's `localOnly` banner is a leftover from the pre-backend prototype and `GET /api/admin/content` always returns `localOnly: false`.

## Language

The app is bilingual (English / Filipino), switched by `components/LanguageToggle.jsx` in `AppHeader` and in the login plate band. **`t()` must be callable outside React** - `lib/driving/stepGoals.js` produces learner-visible status inside a `useFrame` loop against refs - so the language is a module store, not a context: `lib/language.js` (localStorage + a `gearview-language-change` event + subscribers), the same mechanism `progressService.js` uses. `createContext` appears nowhere in `frontend/src`; keep it that way.

**The pure/browser split is load-bearing.** `i18n/translate.js` is pure - no React, no localStorage, no document - because `data/hubContent.js` and `data/vehicleProfile.js` read their defaults through it and `data/` is backend-importable by contract. `i18n/index.js` is the browser side (`t()`, `useT()`, `useLanguage()`). `useT()` returns a new function identity per language, so memoised copies don't go stale on a toggle. `lib/language.js` sets `<html lang>` at import time as well as on change, and its `subscribeToLanguage` listener refreshes the cached value - a `storage` event from a second tab never goes through `setLanguage`.

Keys are **flat and dotted**, written out in full in each namespace file (`i18n/en/*.js` + `i18n/fil/*.js`, merged by `i18n/catalog.js`), so grepping a key finds both the call site and the string. `i18n/catalog.test.js` enforces that the two languages declare the same keys with the same `{tokens}`. Fallback is requested language, then English, then the key itself. Plurals are a reserved `count` value selecting `<key>.one` / `<key>.other`; every other "N of M" form is a whole-sentence key with named tokens, because clause order differs between the languages.

**What is NOT translated:** admin-authored content - module titles, briefing markdown, objectives, hints, checklist items, quiz questions and answers, hotspot labels and detail cards, walk-around gauge/device/scenario text. Those stay in whatever language the admin wrote them. The admin dashboard's own chrome is also English.

**The trap that would corrupt saved progress.** `GAUGE_CHOICES` in `components/WalkAroundStep.jsx` is a `{ value, labelKey }` pair, not one string doing both jobs: `value` (`'Normal'` / `'Abnormal'`) is written into the learner's progress and compared against `gauge.answer`, which is admin-authored English in the database. Translating the value would mark every correct answer wrong the moment a learner switched language. Only the label is translated. (`ModuleActivities`' Report / No Action map to booleans, so they are safe to translate outright.)

Three maps hold **keys rather than sentences** for the same reason - they are read on a per-frame path, or double as an existence check, or live in a file the backend imports: `PHASE_TITLE_KEYS` (`lib/walkAroundStep.js`, which is also the "is this a real phase" test), the parking status set by `lib/driving/stepGoals.js`, and `PALLET_STATE_LABEL_KEYS` / `GRIP_LABEL_KEYS` in `lib/driving/constants.js`.

**Code-owned defaults with an admin override take a `lang` argument**, the same shape in both places: `HUB_CONTENT_FIELDS[].default(context, lang)` in `data/hubContent.js` and `defaultVehicleProfile(lang)` / `defaultKeyLegend(lang)` / `defaultFailMessages(lang)` in `data/vehicleProfile.js`. Readers gain a trailing `lang = DEFAULT_LANGUAGE`, so nothing breaks between commits. `Equipment.content` overrides are per-language via suffixed keys (see above); `Equipment.simConfig` overrides are single-language for now.

## UI Design Direction

### Page shell — `components/PageLayout.jsx`
Every top-level page (one rendered per route branch in `App.jsx`, not sub-components) should wrap its content in `<PageLayout user={user} onLogout={onLogout} onNavigate={onNavigate}>...</PageLayout>` rather than hand-rolling its own `<AppHeader>` + wrapper `<div>`/`<main>`. `PageLayout` renders `AppHeader` plus a `.page-layout` grid (`gap: 20px`, `width: min(1400px, 100%)`, responsive padding) — this is the single source of truth for page width/padding, so don't redefine those on a per-page container class. `TrainingHubPage.jsx` and `ModuleListPage.jsx` are the reference usages. `NotFoundPage.jsx` is an intentional exception (centered error card, not a content page).

### Learner pages are built from `components/ui/`, not per-page CSS
`LoginPage`, `ModuleListPage` and `TrainingHubPage` are Tailwind over the shared primitives, and their stylesheets were deleted. Compose these instead of writing a new page CSS file: `Card`/`CardMedia` (`ui/card.jsx`), `ProgressBar` (`ui/progress.jsx`), `Badge`/`StatusBadge` (`ui/badge.jsx`), `Button` (`ui/button.jsx`), `Kicker`, `PageState`, `Stat`/`Meter`. The full list with each one's job is the JSDoc on `PageLayout.jsx` — keep the two in sync.

**`ProgressBar` is the only progress bar.** Every bar used to be a hand-rolled div with an inline width and no `role="progressbar"`, so a screen reader announced nothing. The primitive owns `role`, `aria-valuenow/min/max` and `aria-valuetext`, and clamps + rounds internally because computed percentages arrive `NaN` (0/0) or above 100 (an admin-deleted checklist item still in saved progress) and the browser drops an out-of-range value silently. Each call site passes **either** `label` **or** `labelledBy` — never both, never neither.

**App base styles live in `@layer base` and must stay there.** Tailwind's utilities are in `@layer utilities`, and an *unlayered* rule beats a layered one regardless of specificity — so `index.css`'s bare `button { font: inherit }` silently overrode `text-sm`/`font-medium` on every `Button` in the app (they rendered 16px/400), and `h1 { color: var(--text-h) }` rendered a `text-white` heading in the heading colour, invisible on the dark plate. Adding a new global element default outside that layer reintroduces the whole class of bug. Co-located page/component `.css` files are still unlayered and still win over both, which is deliberate.

**Controls carry `font-normal` explicitly** (`ui/input.jsx`), because `Field` and the login page wrap them in a `font-bold` `<label>` and a control with no weight of its own inherits it — which made placeholder text read as a filled-in value.

**Aligning a column across sibling cards uses subgrid, not a hardcoded width.** The hub's numbered path gives its `<section>` `grid-cols-[auto_1fr_auto]` and each `Card` `layout="grid"` + `col-span-full grid-cols-subgrid`, so all three action buttons are exactly as wide as the widest label — 167px in English, 242px in Filipino, and whatever an admin's own CTA text needs, with no code change. `Card`'s `layout` prop owns the display property for the same reason the base styles are layered: two display utilities on one element resolve by stylesheet order, not by the order they are written in the class attribute.

**A clickable card is one tab stop.** Never hand-roll `role="button" tabIndex={0} onClick onKeyDown` on an element containing a real `<button>` — that is nested interactive content inside a widget role, two tab stops for one destination, and the inner button then needs `stopPropagation` to work at all. Use `<Card stretchedAction>` (which is `relative isolate`) with `<Button stretched>` (`after:absolute after:inset-0`): one tab stop, one accessible name, clicking anywhere still works.

**Design direction is the "operator's plate"** — the machine's own signage vocabulary. `--surface-deep` (`#0f172a`) is the stamped dark ground, `--surface-deep-accent` the engraved cyan on it, and `--status-done` / `--status-progress` / `--status-todo` / `--status-track` are status in ISO 7010 terms. All are in `index.css`'s `:root` and bridged in `@theme`; the 14 stylesheets still hardcoding `#0f172a` can adopt `var(--surface-deep)` incrementally. **One plate per page** — the hub hero and the login card band — with flat white cards below it.

**The hub plate carries the equipment's artwork.** `PlateArtwork` in `TrainingHubPage.jsx` renders `Equipment.imageUrl` (edited in Equipment Settings as "Hub artwork image URL") bleeding off the plate's right edge, `invert(1)` + `mix-blend-mode: screen` + a left-fading mask. Those images are black technical line drawings on white, so inverting gives white lines and screen blending drops the white ground into the panel — what survives is the wireframe, in the parts-diagram vernacular the tool is about, rather than a photo pasted on. It relies on `Card`'s `overflow-hidden` for the crop. A blank `imageUrl` renders no artwork and the copy column relaxes to full width, so the plate never has a stranded column beside empty space.

**One typeface, sentence case, no small-caps.** `--sans` is Plus Jakarta Sans and `--heading` aliases it; there is no display face and no `--font-condensed`. Hierarchy is size, weight and colour only. A condensed second face with uppercase letterspaced micro-labels (`PROGRESS`, `67% COMPLETE`) was built and rejected — it read as a separate, ill-fitting system, and all-caps flattens word shapes, which costs reading speed for an audience often reading in a second language. Don't reintroduce either. The family stops at **800**, and `:root` sets `font-synthesis: none`, so `font-black` (900) renders no heavier than 800 — use `font-extrabold`.

**The app is laptop/desktop only.** `App.jsx` renders `components/DesktopOnlyNotice.jsx` instead of the app below `DESKTOP_MIN_WIDTH` (1024px, exported from that file with its media query). The gate wraps `App` rather than sitting inside it, so a phone or portrait tablet never mounts the app at all — no session restore, no progress hydration, no content fetches. The notice carries the language toggle, since it is the only screen those visitors can reach. Design for ≥1024px; there is no phone or portrait-tablet layout to maintain, and `hooks/useMediaQuery.js` is the hook for any other query-driven component swap.

Full-width simulation pages (`GenericModulePage`, `PartsIdentificationPage`) wrap their content in `components/SimulationPageLayout.jsx` (sticky header + back button + title block) instead of `PageLayout` — that component owns the `module-page-*` shell classes in `SimulationPageLayout.css`. `GenericModulePage.jsx` is the reference implementation for module UI: guided step-by-step simulation on `ModuleSimulationShell` (objectives/steps sidebar, center scene via `renderScene`, current-task panel via `renderTask`, per-step gating via `canProceed`).

## Notes
- Path alias `@` → `frontend/src` is configured in `vite.config.js` but most existing files use relative imports — either style works.
- Styling is plain CSS files co-located per component/page (`X.jsx` + `X.css`), plus Tailwind (v4, via `@tailwindcss/vite`). The admin dashboard and the learner pages above are Tailwind + `components/ui/`; the simulation, viewer and remaining learner surfaces are still their own CSS files.
- **There is a test runner**: `npm test` in `frontend/` runs `node --test src/**/*.test.js` over the `lib/*.test.js` and `i18n/*.test.js` suites, with `test-helpers/browserGlobals.js` shimming `localStorage`/`window` for modules that read them at import time. `npm test` in `backend/` runs `test/*.test.js`.
